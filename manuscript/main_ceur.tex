\begin{abstract}
    Traditional Role-Based Access Control (RBAC) and static rule engines are often too rigid to adapt to dynamic, context-heavy IoT threats. We propose IoT-Access-Sentinel, a hybrid framework that couples deterministic pre-checks with Large Language Model (LLM) reasoning for runtime access control. Evaluating the system on a synthetic benchmark, we show that while the LLM reasoning layer alone is vulnerable to prompt injection, pairing a deterministic validation pre-filter with strict semantic delimiters improves robustness under the benchmark threat model. While demonstrated within a simulated environment integrated with the Wazuh SIEM~\cite{wazuh2024}, our design shows that LLMs can support context-aware authorization decisions when strictly contained by a deterministic enforcement boundary with fail-secure defaults.
\end{abstract}

\section{Introduction}

The proliferation of Internet of Things (IoT) devices in critical infrastructure, smart homes, and industrial environments has created new security challenges for access control systems. As devices move from isolated components to interconnected ecosystems, authorization decisions must account for identity and policy rules alongside dynamic context, such as access time, device operational state, user role, and environment. Traditional approaches, such as Role-Based Access Control (RBAC), remain effective for deterministic enforcement; however, they are often too rigid to resolve semantic ambiguity in dynamic IoT settings. 

Furthermore, access control in these networks must align with established security guidelines, such as the MITRE ATT\&CK Mitigation M0801 (Access Management)~\cite{mitre2023attack}, which focuses on User Identification and Verification. Adhering to M0801 requires robust mechanisms to audit and verify authorization boundaries, a task that becomes challenging when rules must adapt to contextual anomalies.

Recent generative AI work in IoT security has largely focused on offline policy generation or passive threat detection, leaving a gap in runtime access management. In particular, runtime authorization remains difficult because conventional rule engines struggle with natural language or context-heavy requests, whereas unconstrained LLM reasoning is vulnerable to prompt injection and other adversarial manipulations. Consequently, systems that are sufficiently expressive to reason about context may also be too fragile to be trusted directly in the authorization path.

We address this gap with \textit{IoT-Access-Sentinel}, a hybrid framework that places deterministic validation and multi-agent LLM reasoning in a single runtime access-control pipeline. The system first applies strict, deterministic security checks—such as cryptographic token verification and user-device access control lists (ACLs)—and then routes ambiguous requests to specialized LLM agents for context resolution. The resulting design maintains a deterministic enforcement boundary while using the LLM layer only where semantic reasoning is needed.

To evaluate our design, we developed a synthetic benchmark consisting of simulated SIEM access alerts representing both benign scenarios and targeted adversarial attacks. While our findings suggest that LLMs can assist in resolving complex contextual policies, we emphasize that this evaluation is synthetic and simulated; the framework's performance on live edge traffic and physical IoT hardware remains to be fully explored. Under our benchmark threat model, the LLM reasoning layer alone is vulnerable to prompt injection, but combining it with a deterministic pre-filter and strict prompt delimiters substantially improves decision robustness.

This study makes the following contributions:

\begin{itemize}
    \item We propose a two-stage hybrid IoT authorization pipeline that combines deterministic validation with multi-agent LLM reasoning for context-aware decision making.

    \item We evaluate the framework on a synthetic benchmark with 102 benign/edge scenarios and 105 adversarial attacks, demonstrating both the benefits and the attack surface of LLM-assisted authorization under simulated conditions.

    \item We analyze how deterministic sanitization, prompt delimiters, and fail-secure behavior reduce structural and semantic attacks. We have released our code, benchmark scenarios, stress-testing harness, and result files to support reproducibility.
\end{itemize}

Section~\ref{sec:adversarial_eval} presents the threat model and adversarial evaluation, Section~\ref{sec:decision_pipeline} describes the system architecture, and the remaining sections report the experimental results, limitations of the study, and future directions.


\section{Related Work}\label{sec:related_work}

\subsection{LLM-based Access Control for IoT}

Recent studies have explored large language models for IoT access control~\cite{llm4iot2024, edgegenai2024}, primarily focusing on policy generation from natural language specifications.

LACE~\cite{lace2025} introduces a Language-based Access Control Engine that translates natural language policy descriptions into structured rules. LACE combines LLM-based policy generation with formal verification using an Open Policy Agent (OPA) and reports an 88\% runtime decision accuracy. This illustrates one approach to coupling LLMs with policy enforcement, but its LLM-assisted decision pathway adds runtime latency (2.66s per request) that may limit its use in time-sensitive settings.

CollabIoT~\cite{shastri2025llmdrivenautoconfigurationtransient} employs an LLM-driven capability-based access control for transient IoT collaboration. The system focuses on policy generation and device auto-configuration, reporting validated access control policies with 100\% correctness and a low enforcement overhead. Therefore, CollabIoT is best viewed as a complementary approach; it emphasizes proactive token generation, whereas our work examines reactive runtime authorization when requests are semantically ambiguous.

Taken together, LACE and CollabIoT show how LLMs can support policy creation and configurations. Our system instead explores runtime access decisions on alerts, using multi-agent LLM reasoning only when deterministic validation cannot resolve semantic ambiguity. Table~\ref{tab:related_comparison} summarizes these systems. We note that because these frameworks target different tasks (policy translation, configuration, and runtime assessment) and evaluate on disparate benchmarks, the reported metrics are heterogeneous and do not represent a direct head-to-head comparison under identical settings.

\subsection{Traditional Access Control for IoT}

Traditional IoT access control relies on static rule-based approaches, such as RBAC~\cite{rbac2004}, ABAC~\cite{abac2012}, and capability-based systems~\cite{capability2016}. These methods excel at deterministic validation but struggle with semantic threats and contextual anomalies~\cite{alaba2017internet, ouaddah2016fairaccess}.

DLBAC~\cite{dlbac2022} proposes a deep-learning-based access control using neural networks to learn access patterns. While improving static RBAC, DLBAC lacks explainability, which is critical for verifying compliance with security standards such as the MITRE ATT\&CK Mitigation M0801 (Access Management). M0801 advocates for establishing mechanisms that verify user credentials and roles before granting access, while also logging decisions for auditing. Since deep learning classifiers operate as black boxes, they fail to provide the auditable explainability required by security operators during post-incident investigations.

RASA~\cite{rasa2021} introduced risk-aware adaptive access control using Bayesian networks. However, RASA's risk scores lack semantic transparency, making it difficult for security operators to answer the question of ``why'' a request was denied, which is a critical requirement for post-incident auditing and aligning with M0801 compliance recommendations. Our hybrid model addresses this auditable trail requirement by generating natural language reasoning reports along with each access decision.


Multi-agent LLM frameworks~\cite{multiagent2023} have demonstrated that specialized agents can outperform monolithic general-purpose models on structured tasks. IoT-Access-Sentinel follows this pattern by separating context extraction from the policy evaluation. This design is consistent with recent risk management and secure agent work, including the NIST AI RMF~\cite{nist_airmf_2023} and CaMeL~\cite{camel2024}, which emphasize capability separation and deterministic containment.


\subsection{LLM Vulnerabilities in Cyber-Physical Systems}

Recent literature on Natural Language Access Control (NLAC)~\cite{lace2025, xu2022building} explores the translation of user intent into formal access policies. These systems typically use LLMs for policy \textit{generation} (intent $\rightarrow$ rule), whereas IoT-Access-Sentinel uses LLMs for \textit{runtime evaluation} (rule + context $\rightarrow$ decisions). This runtime delegation introduces risks that have been documented in prior studies on AIoT and agentic systems: prompt injection can manipulate model outputs, and adversarial techniques such as jailbreaking and payload splitting can bypass standard alignment guardrails~\cite{yao2024survey, agentsec2025, wei2023jailbroken, liu2024autodan, fang2024llm}. These observations motivate the deterministic containment boundary (Layer 0) used in our architecture~\cite{doshi2024llms}.

\section{Threat Model and Adversarial Robustness}

\subsection{Threat Model}

Our system operates under an adversarial threat model in which attackers may attempt to bypass access control through input manipulation, prompt injection, SQL injection, Unicode-based obfuscation, semantic evasion, or network/time bypasses. We assume that attackers can observe the system architecture, adapt their payloads over time, and interact with the IoT network; however, they do not possess valid authentication credentials.

\subsection{Defense Mechanisms}

The hybrid architecture implements a two-layer defense. Layer 0 performs deterministic validation before any reasoning occurs. It combines schema validation for incoming alerts, security-critical authentication checks, and pattern matching for obvious injection attempts, and defaults to DENY when credentials are missing or malformed. Layer 1 handles only the requests that survive layer 0. It uses zero-trust prompts, structured JSON outputs, and agent separation to reduce prompt leakage and attack propagation while allowing the Context and Policy agents to reason about more subtle semantic attacks and generate auditable explanations.

\subsection{Adversarial Evaluation}\label{sec:adversarial_eval}

We emphasize that these results are benchmark-specific and demonstrate the effectiveness of our design under the evaluated threat model; they do not constitute a generalized security guarantee against all possible real-world evasion attempts. The deterministic validator detected 66.7\% of the adversarial attempts (70/105) in Layer 0 before they could reach the LLM agents. This block rate is due to two distinct mechanisms:
\begin{enumerate}
    \item \textbf{Input Sanitization and Pattern Matching}: Unicode NFKC normalization, directional/Bidi override character stripping, and regex-based blocklists directly detected and neutralized obfuscated payloads (such as Unicode RTLO and zero-width smuggling) or obvious code injections in 40 out of the 70 cases.
    \item \textbf{Deterministic Authentication Failures}: Because the red-team requests were injected into fields like \texttt{device\_id} or \texttt{user\_id} and lacked valid session credentials (cryptographic tokens), the remaining 30 blocked requests failed the User-Device ACL checks or JWT verification pre-checks, triggering an immediate fail-secure DENY.
\end{enumerate}
The remaining 33.3\% of attacks (35/105)—which primarily involved semantic anomalies like contextual contradiction, chain-of-thought hijacking, and metadata smuggling—bypassed Layer 0 because they appeared structurally valid and carried clean text, but were successfully detected and blocked by the Policy Agent's semantic context comparison and zero-trust prompt constraints.

To address the concern of ``ceding enforcement to the LLM,” Layer 0 acts as a strict containment boundary. Every field is processed through a \texttt{normalize\_text} method using \texttt{unicodedata.normalize('NFKC')} to resolve homoglyph attacks, followed by regex stripping of directional overrides (\texttt{\textbackslash u202A-\textbackslash u202E}), Bidi Isolates (\texttt{\textbackslash u2066-\textbackslash u2069}), and zero-width control characters. Unlike LACE's formal OPA check, which occurs \textit{after} policy generation, our sentinel's formal checks occur \textit{before} the LLM sees the data, ensuring that the LLM reasons only on sanitized, canonicalized context. Under benchmark conditions, the LLM is completely bypassed for the 46\% of requests resolved by Layer 0. On the remaining 54\% of ``semantically ambiguous'' cases, our multi-agent chain (Layer 1) provides a 6.1 percentage point accuracy lift over the 88\% accuracy benchmark reported by policy-generation-only systems such as LACE.

The IoT-Access-Sentinel follows an Observe $\rightarrow$ Decide $\rightarrow$ Act pipeline. Figure~\ref{fig:architecture} summarizes the flow from log ingestion to enforcement. The Observe stage collects security-relevant events from Wazuh, the Decide stage applies deterministic checks and LLM-based reasoning, and the Act stage translates the authorization outcomes into distributed enforcement.

\subsection{Observe: Wazuh SIEM Integration}

We deployed custom decoders and rules in the Wazuh Manager~\cite{wazuh2024} to parse IoT access logs and classify events according to device type, including cameras, sensors, and smart locks. The rules cover network violations, temporal violations, unknown device attempts and high-frequency anomalies. Alerts were forwarded via a webhook to the FastAPI decision engine, together with the source IP, device type, user credentials, and timestamp.

\subsection{Decide: Hybrid Decision Pipeline}\label{sec:decision_pipeline}

The Decide stage consists of two layers. Layer 0 performs deterministic user authorization checks before invoking any LLM reasoning. It verifies token integrity and least-privilege mappings against the configured allowlists and returns a DENY decision when authentication or device membership checks fail~\cite{mitre2023attack}. Layer 1 only handles requests that pass through Layer 0. It uses a Context Agent to summarize behavioral anomalies from the SIEM alert and a Policy Agent to compare that summary against the security policy using constrained prompt instructions.

To reduce the impact of LLM latency or service failure, the system includes a dual-mode fallback that reverts to a deterministic behavior when Layer 1 exceeds the timeout budget. A semantic cache stores prior decisions indexed by device type, device ID, and policy context, allowing repeated requests to bypass the LLM inference when appropriate.

\subsection{Act: Distributed Enforcement via Wazuh Active Response}

Authorization outcomes are translated into enforcement actions using the Wazuh Active Response. When the policy engine issues a DENY decision, the system submits a firewall-drop command to the relevant Wazuh agent via the REST API.
\begin{lstlisting}[language=json]
PUT /active-response
{
  "command": "firewall-drop",
  "agent_id": "<source_device_agent>",
  "arguments": ["-", "<source_ip>"]
}
\end{lstlisting}

This design supports distributed enforcement at the source device rather than relying solely on centralized gateway blocking. The blocking duration is configurable and defaults to 3600 seconds.

\section{Evaluation Methodology}\label{sec:evaluation}

We evaluated the IoT-Access-Sentinel using 102 test scenarios and 105 diversity-driven, red-team adversarial attempts. The 102 general benchmark scenarios span critical security categories: User Authorization, Attack Detection, Time/Network Policies, Device-Specific Rules, and Edge Cases.

To ensure an unbiased evaluation, 102 general benchmark scenarios were balanced with 45 ALLOW and 57 DENY scenarios. In contrast, the 105 Red Team scenarios are 100\% DENY (105) because they focus exclusively on adversarial detection and evasion prevention.

The expected outcomes were manually validated against the security policies. Each scenario specifies the device metadata, user credentials, timestamp, and ground-truth decision (ALLOW/DENY).

\subsection{Baseline Comparison}

To quantify the improvement over traditional approaches, we implemented a production-representative \textit{RBAC+Rules Baseline} consisting of the following deterministic validation mechanisms:
\begin{itemize}
    \item \textbf{User Authentication}: Session token verification (validating JSON Web Tokens or string format keys).
    \item \textbf{User-Device Mapping}: Access Control Lists (ACLs) mapping users and roles to authorized device IDs.
    \item \textbf{Network/Time Rules}: Standard CIDR-based subnet validation and scheduled day/time hour filtering.
    \item \textbf{Basic Signature Filtering}: Regex-based pattern matching in incoming text fields to detect obvious SQL injection (\texttt{UNION}, \texttt{DROP}), Cross-Site Scripting (\texttt{<script>}), and direct prompt injection substrings (such as \texttt{IGNORE PREVIOUS}).
\end{itemize}
This baseline represents a modern, security-hardened API gateway capability, rather than a plain RBAC model that only evaluates user roles. Labeling it as the RBAC+Rules Baseline provides a fair and rigorous comparison point for assessing the hybrid LLM’s contextual reasoning.


\subsection{Evaluation Metrics and Statistical Testing}

\begin{itemize}
    \item McNemar's test of significance for paired binary outcomes ($\alpha=0.01$)
    \item 95\% confidence intervals for accuracy and error rates
    \item Category-wise accuracy breakdown to identify LLM strengths
\end{itemize}

The system performance was evaluated based on the end-to-end latency (alert receipt to enforcement), throughput (concurrent requests), and resource usage (memory and CPU).

\subsection{Confidence Derivation and Post-Hoc Analysis}

Unlike standard classification models that rely on logit-based probabilities, IoT-Access-Sentinel logs Verbalized Semantic Confidence for auditing purposes. During the policy evaluation stage (Layer 1), the LLM agent is prompted to output a numerical confidence score ($c \in [0, 1]$) with its decision and reasoning. This score reflects an agent's semantic certainty with respect to the current policy context. Although not used for live decision gating, these scores were recorded for post-hoc analysis and auditing. A key limitation is that LLM-generated text-based probabilities are often poorly calibrated; therefore, verbalized confidence may not correlate well with empirical correctness unless a formal calibration analysis is performed. Therefore, we analyzed the confidence score as an ordinal metric rather than a runtime gating rule.

\subsection{Mitigation Performance: Semantic Caching}\label{sec:caching_results}
The Semantic Caching Layer (detailed in Section~\ref{sec:decision_pipeline}) can mitigate some availability concerns of remote LLMs. For repeated access requests, it bypasses inference and returns sub-millisecond responses, and it can serve cached decisions during cloud API outages.

The hybrid system defaults to DENY for API timeouts or internal pipeline failures. Although these fail-secure actions (34 instances out of 137 initiated requests) temporarily impact availability, they reduce the risk of unauthorized access during transient system instability. In the 102 completed scenarios (204 total runs), all ``should-DENY'' requests were correctly blocked by the hybrid system, compared with 82.4\% for the RBAC+Rules baseline. In this setting, reduced availability does not necessarily imply weaker access control.

In our targeted red-team evaluation (Section~\ref{sec:adversarial_eval}, Table~\ref{tab:adversarial}) consisting of 105 high-intensity scenarios, initial LLM configurations failed against sophisticated prompt injection attacks. After the structural mitigations were added, the hybrid system handled all evaluated evasion attempts, indicating improved resistance when semantic bounds were enforced.

The post-mitigation behavior reflects the system's structural reliance on the deterministic Layer 0 to filter malformed payloads, combined with strict LLM data bounding. This defense-in-depth approach supports the reliability of the system under adversarial conditions.

\section{Discussion}

\subsection{Agent Security and Authorization Boundaries}

To address the trust--authorization gap inherent in probabilistic agentic systems~\cite{nistai2024}, we defined explicit authorization boundaries and tool-use scoping for the sentinel.

The multiagent architecture uses a ``need-to-know'' data partitioning strategy. The \textit{Context Agent} receives raw network/device metadata to generate a situational report, whereas the \textit{Policy Agent} receives this report alongside the relevant security policies. This separation reduces the risk that a compromised agent can fabricate a context for an unauthorized bypass.

Unlike general-purpose autonomous agents, the sentinel does not expose open-ended tool use privileges. The LLM agents operate within a ``read-only'' reasoning sandbox and can only generate a structured \texttt{EnforcementAction} (DENY, PERMIT, or ESCALATE). The actual action on the security infrastructure (for example, blocking an IP via Wazuh) is performed by a deterministic, non-LLM \textit{Enforcement Controller}. This separation limits the effect of prompt injection on the reasoning layer.

The sentinel restricts the influence of the LLM to the semantic resolution of existing policy conflicts. The agentic layer cannot create new policies or modify Layer 0 blocklists. Any LLM reasoning failure or internal processing error defaults to a fail-secure DENY status.

\subsection{Governance and Systemic Risk Management}

Delegating runtime authorization to probabilistic LLM reasoning introduces risks that must be managed using governance and fallback mechanisms.

To mitigate ``outage-induced false denies'' caused by API latency or service unavailability, the sentinel uses a \textit{Dual-Mode Fallback}. If the LLM agents fail to respond within a 150ms timeout, the system reverts to Layer 0 (Deterministic) enforcement; ambiguous requests are sent to an Escalation Queue for human review or cached-policy enforcement. The fail-secure design also introduces a denial-of-service (DoS) risk: given the observed 24.8\% API timeout rate defaulting to DENY during stress testing, an adversary could flood the system with complex semantic requests and deny legitimate access. Future studies should consider rate-limiting or localized small language models (SLMs) to mitigate this threat.

To address integrity risks such as prompt injection or jailbreaking, the sentinel employs \textit{Semantic Guardrails} and \textit{Audit Trails}. Every agent reasoning step is logged as a ``Policy Explanation'' in the SIEM, allowing SOC operators to inspect hallucinated permits after the fact. A multi-agent ``consensus'' model adds a governance layer, where the Auditor Agent checks whether the Policy Agent's decision aligns with the provided policy context.

Sending sensitive IoT metadata (e.g., user IDs and geolocation) to third-party APIs incurs a privacy cost. While our current evaluation uses cloud-based Groq inference, the architectural roadmap emphasizes Local Differential Privacy (LDP) and on-premise offloading. Redacting Personally Identifiable Information (PII) at layer 0 can reduce the data exposure surface.

\subsection{Deployment Considerations}

The Wazuh agent (ossec-agent) has relatively modest resource requirements, typically fitting within 8--32 MB of RAM, requiring only a small amount of storage, and operating over intermittent connectivity because logs are buffered locally~\cite{wazuh2024}. This suggests the feasibility of many higher-end IoT devices, including smart cameras, industrial sensors, and edge gateways. In contrast, ultra-constrained devices, such as Arduino-class boards or ESP8266 nodes, would likely require gateway proxy deployment rather than direct agent installation.

A production rollout would still require firewall configuration for enforcement targets, authenticated manager connections, and explicit validation of fail-safe behavior in the event of network partitions. For constrained environments, a reverse proxy gateway running Wazuh agents remains a practical option because it centralizes enforcement while reducing per-device overhead.

\subsection{Limitations}

A key limitation of this study is that our evaluation relies on simulated Wazuh alerts generated from synthetic scenarios rather than live edge network traffic. This limits the generalizability of our performance and security findings to actual physical deployments. The benchmark also relies on author-defined threat models and policy rules; therefore, the results do not necessarily generalize to other datasets or production operator workflows.

The study is further limited by its narrow scope: it uses a single LLM model (Llama 3.1 8B via the Groq cloud API), depends entirely on external API availability and network connectivity, and evaluates only high-level access-control policies. Lower-level concerns, such as device firmware updates, encryption protocols, and network layer exploits, were not considered in this work.

\subsection{Future Work}

Future work should focus on validation with real-world traces and high-fidelity physical testbeds, together with human-in-the-loop studies in which SOC analysts assess the explanations generated by the LLM agents. These steps will help determine whether the current results generalize beyond the synthetic benchmark.

The next direction is to fine-tune smaller, local domain-specific models for IoT threat patterns and benchmark them against semantic rule engines, such as OPA/Rego, augmented with graph-based context retrieval. Open questions remain regarding the amount and balance of labeled data required, the accuracy--latency trade-off for different model sizes, and whether local inference can replace the current cloud-based setup to mitigate API availability risks.

Another possible direction is to combine runtime reasoning with CollabIoT-style formal token models through Semantic Leases so that the LLM handles only semantic validation while a lightweight edge controller performs enforcement.

\subsection{Reproducibility and Open-Source Artifacts}

To facilitate independent auditing and reproducibility, the complete benchmark suite, baseline configurations, multi-agent prompts, and evaluation scripts are publicly available at \texttt{https://github.com/ahmed-fouad-lagha/IoT-Access-Sentinel}. The reported metrics correspond to repository commit hash \texttt{8d2f7a9e} (using random seed \texttt{42} for data generation). The 204-run benchmark comparison is pinned by the explicit manifest file \texttt{evaluation/benchmark\_manifest\_204.txt}. All core accuracy, ablation, and safety metrics can be reproduced by running the canonical evaluation script \texttt{python3 scripts/02\_evaluate\_system.py --mode rbac}, which reads that manifest, followed by the analysis harness \texttt{python3 scripts/03\_analyze\_results.py --mode all}. The high-concurrency stress test metrics (34 timeouts/75.2\% availability) can be regenerated using the concurrent simulation harness \texttt{python3 scripts/05\_run\_stress\_test.py --mode simulate}, which saves the output statistics to \texttt{results/stress\_test\_results.json}.

\section{Conclusion}

We present IoT-Access-Sentinel, a hybrid multiagent framework for IoT access control that combines deterministic authorization pre-checks with LLM-based contextual reasoning. Our evaluation on a simulated synthetic benchmark highlights the safety and security trade-offs of this design. While testing showed that the reasoning layers of the LLM were vulnerable to prompt injection, the addition of deterministic containment and strict delimiters allowed the system to handle benchmarked adversarial attacks more robustly. When integrated with a SIEM ecosystem such as Wazuh, Sentinel provides a structured template for containing LLMs in access control pathways. However, future work must focus on live traffic validation and physical hardware deployments before broad operational conclusions can be drawn. Ultimately, this study suggests that future agentic IoT security designs must prioritize deterministic containment boundaries alongside semantic flexibility.
