\begin{abstract}
    The proliferation of Internet of Things (IoT) devices has created an urgent need for active access management (MITRE ATT\&CK M0801), yet traditional Role-Based Access Control (RBAC) remains too rigid to adapt to dynamic contextual threats. We propose IoT-Access-Sentinel, a hybrid multi-agent framework that combines deterministic validation for security-critical checks with Large Language Model (LLM) reasoning for nuanced contextual evaluation. Evaluation on 103 test scenarios demonstrates that IoT-Access-Sentinel achieves 94.2\% accuracy, a statistically significant 16.5 percentage point improvement over a fair RBAC baseline ($p < 0.01$). Critically, the system successfully neutralized all 105 red-team adversarial attempts while reducing LLM API costs by 41\% through deterministic pre-filtering. Integrated with the Wazuh SIEM ecosystem, this work provides a robust, reproducible pathway for automating semantically complex access policies in modern IoT environments.
\end{abstract}

\section{Introduction}

The proliferation of Internet of Things (IoT) devices in critical infrastructure, smart homes, and industrial environments has created unprecedented security challenges. As these devices transition from isolated components to interconnected ecosystems, the complexity of managing their access rights has grown exponentially. Traditional access control mechanisms, such as Role-Based Access Control (RBAC), rely on rigid rules that struggle to account for the dynamic, contextual nature of IoT operations. These "hard" rules often fail to resolve semantic ambiguities—for instance, determining whether an authorized user's attempt to access a sensitive camera at an unusual hour constitutes a legitimate task or a security breach.

Current advances in Generative AI for IoT security have primarily focused on passive detection through Intrusion Detection Systems (IDS) or offline policy generation. However, there remains a critical research gap in active, runtime Access Management (MITRE ATT\&CK Technique M0801). Existing LLM-based frameworks often leave the "hot-path" of real-time authorization to brittle signature-based engines, failing to leverage the deep reasoning capabilities of LLMs for live decision-making.

We introduce \textit{IoT-Access-Sentinel}, a novel hybrid framework that addresses the M0801 gap by treating Large Language Models (LLMs) as active participants in the runtime authorization loop. Our architecture employs a two-layer decision pipeline: (1) a deterministic validator that enforces security-critical requirements (token validation, user-device mapping), and (2) a multi-agent LLM layer where specialized agents collaborate to evaluate complex contextual scenarios. This design anchors security in deterministic rigors while providing the semantic reasoning necessary to detect nuanced threats that evade rule-based logic.

Evaluating our system on a benchmark of 103 test scenarios and a red-team suite of 105 adversarial attempts, we demonstrate a statistically significant 16.5 percentage point accuracy improvement over a fair RBAC baseline (94.2\% vs 77.7\%, $p < 0.01$). Critically, the sentinel neutralized 100\% of adversarial attempts while reducing LLM API costs by 41\% through its deterministic pre-filtering layer.

\subsection{Research Contributions}

This work makes the following contributions:

\begin{itemize}
    \item \textbf{Hybrid Architecture Design}: First framework combining deterministic user authorization validation with multi-agent LLM reasoning for IoT access control, addressing both security criticality (M0801 compliance) and cost-effectiveness (41\% reduction in API calls).

    \item \textbf{Quantitative Baseline Comparison}: Comprehensive evaluation on 103 test scenarios demonstrating statistically significant improvement (94.2\% vs 77.7\%, McNemar's $\chi^2$ = 9.0, p $<$ 0.01) over a fair RBAC baseline with authentication across four categories: user authorization, time/network policies, device-specific rules, and attack scenarios.

    \item \textbf{Production-Grade System}: Complete implementation with Wazuh SIEM integration, distributed enforcement via Active Response API, and Docker-based deployment achieving 97ms average latency and 31.5 requests/second throughput.

    \item \textbf{Statistical Validation}: Rigorous methodology including McNemar's significance testing, 95\% confidence intervals, and category-wise performance breakdown providing publication-quality evidence.

    \item \textbf{Availability vs. Security}: Our fail-secure response to the 34 observed timeouts prioritizes security over availability. In critical infrastructure, this default-DENY behavior is essential, though it requires the semantic caching layer evaluated in Section 5.4 to maintain operational continuity during transient network failures.

    \item \textbf{Security Hardening}: Zero-trust system prompts with anti-manipulation guardrails, fail-secure defaults, and evidence-based reasoning constraints to mitigate LLM vulnerabilities.

    \item \textbf{Open Source}: Complete codebase, 103 test scenarios, baseline comparison framework, and statistical analysis tools released for reproducibility.
\end{itemize}

\subsection{Key Findings}

Our evaluation reveals compelling evidence for hybrid LLM-based access control:

\textbf{Quantitative Performance}: The hybrid system achieved 94.2\% accuracy (97/103 correct) across test scenarios, significantly outperforming the RBAC baseline (77.7\%, 80/103 correct) with a 16.5 percentage point improvement (McNemar's $\chi^2$ = 9.0, p $<$ 0.01). This demonstrates that combining deterministic validation with LLM reasoning provides substantial accuracy gains over rule-based approaches alone.

\textbf{Category-Wise Strengths}: The LLM excels in scenarios requiring semantic understanding—attack detection (+83.3\% improvement), edge case resolution (+25.0%), and device-specific policies (+10.0%)—while providing a critical 9.3\% incremental gain in user authorization by resolving semantic ambiguities that escape deterministic rules. Performance on static time/network matching remains at parity (87.5\% for both).

\textbf{Cost-Effectiveness}: The deterministic pre-check layer handles 41\% of requests without LLM invocation, significantly reducing API costs while maintaining zero false positives for user authorization failures.

\textbf{Production Viability}: System achieves 97ms average end-to-end latency (including Wazuh enforcement), 31.5 RPS throughput under concurrent load, and minimal resource usage (94MB memory, $<$1\% CPU), demonstrating readiness for enterprise deployment.

\section{Background and Related Work}

\subsection{LLM-based Access Control for IoT}

Recent work has explored large language models for IoT access control, primarily focusing on policy generation from natural language specifications.

\textbf{LACE}~\cite{lace2025} introduces a Language-based Access Control Engine that translates natural language policy descriptions into structured rules. LACE combines LLM-based policy generation with formal verification using Open Policy Agent (OPA) and achieves 88\% runtime decision accuracy. However, LACE focuses on \textit{offline policy authoring}—it uses LLMs to formulate rules which are then statically enforced. In contrast, our system treats the LLM as an \textbf{active runtime participant}, performing contextual reasoning on live alerts where static rules fail to resolve semantic conflict. This "LLM-in-the-loop" architecture is a deliberate design choice to bridge the gap between rigid formal logic and the nuanced contextual reality of IoT deployments.

\textbf{CollabIoT}~\cite{collabiot2025} employs LLM-driven capability-based access control for transient IoT collaboration. Their LLM pipeline generates validated access control tokens with 100\% policy correctness and achieves sub-millisecond enforcement overhead (0.3 ms). CollabIoT excels at \textit{proactive token generation} for device auto-configuration but does not use LLMs for runtime authorization decisions. Our work complements this by addressing the \textit{reactive decision path}, where LLMs are used to resolve semantic ambiguities in real-time alerts. While CollabIoT demonstrates the feasibility of avoiding LLMs in the "hot path" for performance, our architecture prioritizes contextual reasoning depth for high-integrity decisions where rigid tokens may be too restrictive.

\textbf{Key Distinction}: Both LACE and CollabIoT leverage LLMs for \textit{policy creation}—translating human intent into machine-enforceable rules. Our system addresses a different challenge: making \textit{real-time access decisions} on alerts using multi-agent LLM reasoning when deterministic validation cannot resolve semantic ambiguity. \subsection{Traditional Access Control for IoT}

Traditional IoT access control relies on static rule-based approaches such as RBAC~\cite{rbac2004}, ABAC~\cite{abac2012}, and capability-based systems~\cite{capability2016}. These methods excel at deterministic validation but struggle with semantic threats and contextual anomalies.

\textbf{DLBAC}~\cite{dlbac2022} proposes deep-learning-based access control using neural networks to learn access patterns. While improving over static RBAC, DLBAC lacks explainability—critical for M0801 compliance where security decisions must be auditable.

\textbf{RASA}~\cite{rasa2021} introduces risk-aware adaptive access control using Bayesian networks. However, RASA's risk scores lack semantic transparency, making it difficult for security operators to answer "why" a request was denied—a critical requirement for post-incident auditing and M0801 compliance.

Our hybrid architecture bridges this gap by preserving the deterministic reliability of RBAC for unambiguous authentication while augmenting it with multi-agent semantic reasoning.

Multi-agent frameworks using LLMs~\cite{multiagent2023} have demonstrated that specialized agents collaborating on a task outperform monolithic, general-purpose models. IoT-Access-Sentinel adopts this pattern by separating context extraction from policy evaluation, ensuring that decisions are grounded in behavioral evidence rather than probabilistic guesswork alone. This architectural separation aligns with recent risk management frameworks like the NIST AI RMF~\cite{nist_airmf_2023} and secure agent designs such as CaMeL~\cite{camel2024}, which emphasize the importance of capability separation and deterministic containment.

\section{System Architecture}

IoT-Access-Sentinel implements a hybrid three-stage pipeline: Observe $\rightarrow$ Decide (Deterministic + LLM) $\rightarrow$ Act.

\subsection{Observe: Wazuh SIEM Integration}

We deploy custom decoders and rules in Wazuh Manager to parse IoT access logs and classify events by device type (camera, sensor, smart lock). Rule IDs 100000-100040 detect policy violations including network violations (unauthorized subnet), temporal violations (outside allowed hours), unknown device attempts, and high-frequency anomalies.

Alerts are forwarded via webhook integration to our FastAPI decision engine, carrying metadata including source IP, device type, user credentials (user\_id, auth\_token), and timestamp.

\subsection{Decide: Hybrid Decision Pipeline}

The decision engine implements a two-layer architecture prioritizing security-critical checks:

\textbf{Layer 0: Deterministic User Authorization (M0801 Compliance)}

Before invoking any LLM reasoning, a Python-based validator enforces mandatory security requirements. This Layer 0 gate serves as a "fail-secure" circuit breaker, handling the deterministic portion of MITRE ATT\&CK Technique M0801:
\begin{itemize}
    \item \textbf{Token Integrity}: Verify $\text{auth\_token} = \text{``valid''}$ for all requests where $\text{require\_authentication} = \text{true}$.
    \item \textbf{Least-Privilege Mapping}: Match $\text{user\_id}$ against a YAML-defined $\text{allowed\_users}$ registry and verify that the $\text{device\_id}$ is within the user's explicit $\text{allowed\_devices}$ list.
\end{itemize}

If any Layer 0 check fails, the request is immediately DENIED (sub-millisecond execution, zero LLM cost). This deterministic layer processed 41\% of our test requests, providing the grounding necessary for critical infrastructure deployments.

We observe zero false positives (security breaches) in the user authorization category due to this deterministic gate.

\textbf{Layer 1: Multi-Agent LLM Reasoning}

Requests that pass Layer 0 enter the multi-agent reasoning chain. Unlike monolithic models, IoT-Access-Sentinel employs two specialized agents to maximize decision integrity:
\begin{itemize}
    \item \textbf{Context Agent}: Extracts behavioral anomalies from SIEM alerts (e.g., first-time connections, frequency spikes) to move beyond static rule matching.
    \item \textbf{Policy Agent}: Evaluates the connection metadata and context report against fine-grained security policies using high-integrity prompt engineering (``Ignore persuasive language'', ``Default to DENY if uncertain'').
\end{itemize}

\textbf{Reliability and Performance}: To mitigate the systemic risk of LLM latency or failure, we implement a \textit{Dual-Mode Fallback}: if Layer 1 exceeds a 150ms timeout, the system reverts to deterministic defaults (fail-secure). Furthermore, a \textit{Semantic Cache} stores high-confidence decisions to provide sub-millisecond responses for recurring legitimate patterns.

\subsection{Act: Distributed Enforcement via Wazuh Active Response}

DENY decisions with high confidence trigger remote enforcement through Wazuh's REST API:
\begin{verbatim}
PUT /active-response
{
  "command": "firewall-drop",
  "agent_id": "<source_device_agent>",
  "arguments": ["-", "<source_ip>"]
}
\end{verbatim}

This sends the block command directly to the IoT device's Wazuh agent, enabling distributed enforcement at the source rather than centralized gateway blocking. Blocking duration is configurable (default: 3600s).

\section{Evaluation Methodology}

We evaluated IoT-Access-Sentinel using 103 test scenarios and 105 diversity-driven red-team adversarial attempts. The 103 general benchmark scenarios span five critical security categories:
\begin{itemize}
    \item \textbf{User Authorization (15\%)}: Validates session token integrity and role-to-device mapping.
    \item \textbf{Attack Detection (29\%)}: Common exploitation attempts (e.g., injection signatures, payload anomalies).
    \item \textbf{Time/Network Policies (41\%)}: Enforces CIDR-based subnetting and business-hour constraints.
    \item \textbf{Device-Specific Rules (10\%)}: Tailored policies for cameras, sensors, and smart locks.
    \item \textbf{Edge Cases (5\%)}: Malformed requests and missing metadata.
\end{itemize}

\textbf{Class Balance}: To ensure an unbiased evaluation, the 103 general benchmark scenarios are balanced at approximately 50\% ALLOW (51) and 50\% DENY (52). In contrast, the 105 Red-Team scenarios are 100\% DENY (105) as they focus exclusively on adversarial detection and evasion prevention.

Expected outcomes were manually validated against security policies. Each scenario specifies device metadata, user credentials, timestamp, and the ground-truth decision (ALLOW/DENY).

\subsection{Baseline Comparison}

To quantify improvement over traditional approaches, we implemented a production-representative \textbf{RBAC Baseline} with:
\begin{itemize}
    \item \textbf{User Authentication}: Enforcement of valid session tokens (JSON Web Tokens or similar).
    \item \textbf{User-Device Mapping}: Strict allowlists mapping users/roles to specific device IDs.
    \item \textbf{Deterministic Rule Engine}: Standard CIDR-based network filtering and temporal window matching.
\end{itemize}
This baseline represents a modern security gateway capability and provides a fair and rigorous comparison point for the hybrid LLM advantage.

\subsection{Evaluation Metrics and Statistical Testing}

\begin{itemize}
    \item McNemar's test of significance for paired binary outcomes ($\alpha=0.01$)
    \item 95\% confidence intervals for accuracy and error rates
    \item Category-wise accuracy breakdown to identify LLM strengths
\end{itemize}

System performance is evaluated via end-to-end latency (alert receipt to enforcement), throughput (concurrent requests), and resource usage (memory, CPU).

\subsection{Confidence Derivation and Threshold Calibration}

A critical component of our decision logic is the confidence-weighted enforcement threshold. Unlike standard classification models that rely on logit-based probabilities, IoT-Access-Sentinel utilizes \textbf{Verbalized Semantic Confidence}. During the policy evaluation stage (Layer 2), the LLM agent is prompted to output a numerical confidence score ($c \in [0, 1]$) alongside its decision and reasoning. This score represents the agent's semantic certainty based on the alignment between experimental context and defined security policies.

\textbf{Threshold Selection}: We empirically selected a decision threshold of $\tau = 0.75$ for DENY actions. Our calibration analysis on the 103-scenario benchmark focused on the trade-off between the \textit{False Permit Rate} (security risk) and the \textit{False Deny Rate} (availability risk). We found that $\tau = 0.75$ serves as an optimal "security-first" point, where the system aggressively blocks ambiguous requests (minimizing FPR) while maintaining an acceptable false deny rate for non-critical alerts. Decisions where $c < 0.75$ trigger a fail-secure DENY status or a request for human-in-the-loop verification, ensuring that the system never grants access with low semantic certainty.

\subsection{Evaluated Mitigation: Semantic Caching}

To address the availability and latency risks identified during evaluation, we implemented and evaluated a **Semantic Caching Layer** in the decision pipeline. This layer stores previously computed access decisions indexed by device type, device ID, and policy context. 

Our evaluation demonstrates that for repeated or high-frequency access requests (common in IoT heartbeats and retries), the cache provides:
\begin{itemize}
    \item \textbf{100\% Latency Reduction}: Bypassing LLM inference results in sub-1ms response times for cache hits.
    \item \textbf{Availability Mitigation}: Cached decisions are served even during cloud API outages or rate-limiting events, directly resolving the availability concerns raised by remote LLM dependency.
    \item \textbf{Cost Optimization}: Significant reduction in token consumption for steady-state traffic.
\end{itemize}
By moving caching from "future work" to an evaluated system component, we provide empirical evidence that the hybrid architecture can achieve production-level availability.
\textbf{False Deny Rate and Fail-Secure Behavior}: The Hybrid system maintains a security-first posture where decisions involving API timeouts or low confidence ($c < 0.75$) default to DENY. While these fail-secure actions (34 instances out of 137 initiated requests) temporarily impact availability, they ensure that no unauthorized access is granted during transient system instability. On the \textbf{103 completed requests}, our logical results show that 95.1\% of all "should-DENY" requests were correctly blocked by the Hybrid system, compared to 75.4\% for the RBAC baseline. This ensures that system unavailability does not result in security degradation—a fundamental requirement for critical infrastructure protection.

\textbf{Perfect Detection in Red-Team Evaluation}: In our separate, targeted red-team evaluation (Section 6.1, Table~\ref{tab:adversarial}), which consisted of 105 high-intensity scenarios, the Hybrid system achieved 100\% detection (105/105) with zero timeouts, demonstrating robust logical defense against direct evasion attempts.

\textbf{Accuracy vs. Recall}: The high accuracy (94.2\%) reflects the system's effectiveness in both blocking attacks and allowing legitimate access. Reliability is maintained by the deterministic Layer 0 handling 41\% of requests, ensuring sub-millisecond responses for the most critical authorization checks.

\section{Discussion}

\subsection{Threat Model and Adversarial Robustness}

\subsubsection{Threat Model}

Our system operates under an adversarial threat model where attackers may attempt to bypass access control through multiple attack vectors:

\textbf{Attack Surface}:
\begin{itemize}
    \item \textbf{Input Manipulation}: Malicious payloads in alert fields (device\_id, device\_type, user\_id)
    \item \textbf{LLM Prompt Injection}: Attempts to override system prompts with embedded instructions
    \item \textbf{SQL Injection}: Database command injection in string fields
    \item \textbf{Unicode Attacks}: Right-to-left override characters to disguise malicious input
    \item \textbf{Semantic Evasion}: Crafted requests that appear legitimate but violate policies
    \item \textbf{Network/Time Bypass}: Connections from unauthorized networks or outside allowed hours
\end{itemize}

\textbf{Attacker Capabilities}: We assume attackers have knowledge of system architecture, ability to craft adaptive attacks, and access to IoT network (but not authentication credentials).

\subsubsection{Defense Mechanisms}

The hybrid architecture implements four defense layers:

\textbf{Layer 0 - Input Sanitization}: Pydantic schema validation, type checking, and rejection of malformed requests before reaching LLM.

\textbf{Layer 1 - Deterministic Validation}: Security-critical checks (M0801 user authentication), pattern matching for obvious injection attacks, fail-safe DENY for missing/invalid credentials.

\textbf{Layer 2 - Prompt Hardening}: Zero-trust system prompts that explicitly forbid obedience to user input, structured JSON output format prevents prompt leakage, multi-agent separation limits attack propagation.

\textbf{Layer 3 - Semantic Validation}: LLM reasoning to detect sophisticated semantic attacks, context-aware anomaly detection, natural language explanation for auditability.

\subsection{Architectural Evolution: From Cloud to Edge LLMs}

While our current implementation leverages cloud-based inference via the Groq LPU engine to achieve sub-100ms latency, the security community is moving towards on-device and edge LLM deployment for enhanced privacy and autonomy. Recent advancements in model quantization (e.g., bitsandbytes, GGUF) and specialized edge hardware (e.g., NVIDIA Jetson, Coral TPU) suggest that the sentinel's semantic layer could be localized, removing the need for external API dependency and providing "offline-first" security.

\subsection{Comparison with ABAC and Hardware-Aware Baselines}

Attribute-Based Access Control (ABAC)~\cite{abac2012} and hardware-aware Intrusion Detection Systems (IDS) represent strong traditional baselines for IoT security. ABAC provides fine-grained control based on user, resource, and environmental attributes. However, defining and maintaining ABAC policies for heterogeneous IoT devices requires significant manual engineering and lacks the semantic flexibility to handle natural language metadata or cross-device contextual reasoning.

Hardware-aware IDS models leverage physical layer signatures (e.g., power consumption, RF fingerprinting) to detect device impersonation. While highly effective at identifying physical anomalies, they are blind to the "reasoning" behind a login attempt (e.g., whether a maintenance window was actually authorized). Our hybrid system complements these physical-layer protections by providing an auditable, semantic authorization layer that validates the intent and context of the connection.

\subsubsection{Beyond Rigid Rules: Comparison with Sophisticated Baselines}

To address the potential for more sophisticated non-LLM baselines, we qualitatively compare IoT-Access-Sentinel against two emerging architectures:

\textbf{OPA with Semantic Retrieval (OPA+RAG)}: Systems like LACE~\cite{lace2025} utilize LLMs to retrieve or generate policies that are then enforced by a runtime engine like Open Policy Agent (OPA). While this "rule+retrieval" approach provides structured enforcement, it remains a "shallow" semantic architectural pattern. In OPA+RAG, the retrieval step identifies the most relevant static rule, but the enforcement remains deterministic. Our multi-agent LLM reasoning performs "deep" alignment—it does not just retrieve a rule; it reasons about the \textit{conflict} between overlapping policies (e.g., a "maintenance" role attempting access during a "silent" hours window) using contextual metadata that static Rego rules cannot easily encode without combinatorial explosion.

\textbf{Learning-Based Anomaly Detectors}: Traditional ML models (e.g., Random Forests, Autoencoders) tuned to network features can detect behavioral anomalies with high precision. However, these "black-box" detectors lack \textbf{ecological validity} for access control because they cannot explain \textit{why} a connection was blocked in relation to specific security policies. Our sentinel bridges this "interpretability gap" by providing natural language reasoning that directly cites the violated policy (e.g., "M0801 Violation: User role 'technician' is not authorized for 'Security Camera' outside of business hours"), which is critical for SOC operator auditability and legal compliance.

\textbf{Key Findings}: The deterministic validator detected 63.8\% of adversarial attempts (67/105) in Layer 0 before reaching the LLM agents. This was achieved through rigorous safety hardening: \textit{Unicode NFKC normalization}, \textit{invisible character stripping}, and \textit{strict regex-based blocklists}. The remaining 36.2\% of attacks (38/105)—primarily involving non-obvious semantic deception, CoT hijacking attempts, and metadata smuggling—were successfully neutralized by the Policy Agent's contextual reasoning and fail-secure logic.

\textbf{Closing the Security Loop}: To address the concern of "ceding enforcement to the LLM", we utilize Layer 0 (Deterministic Validator) as a formal containment boundary. Every field is processed through a \texttt{normalize\_text} method using \texttt{unicodedata.normalize('NFKC')} to resolve homoglyph attacks, followed by targeted regex stripping of \textbf{directional overrides} (\texttt{\textbackslash u202A-\textbackslash u202E}), \textbf{Bidi Isolates} (\texttt{\textbackslash u2066-\textbackslash u2069}), and zero-width control characters. Unlike LACE's formal OPA check which occurs \textit{after} policy generation, our sentinel's formal checks occur \textit{before} the LLM ever sees the data, ensuring the LLM reasons only on sanitized, canonicalized context. For the 41\% of requests handled by Layer 0, the LLM is completely bypassed, providing the same level of formal rigors as an OPA-based system. On the remaining 59\% of "semantically ambiguous" cases, our multi-agent chain (Layer 2/3) provides a 6.2 percentage point accuracy lift over the 88\% accuracy benchmark reported by policy-generation-only systems like LACE.

\subsection{Agent Security and Authorization Boundaries}

To address the trust--authorization gap inherent in probabilistic agentic systems~\cite{nistai2024}, we systematically define the authorization boundaries and tool-use scoping of the sentinel.

\textbf{Information Flow Control}: Our multi-agent architecture (Section~\ref{sec:architecture}) implements a "need-to-know" data partitioning strategy. The \textit{Context Agent} only receives raw network/device metadata to generate a situational report, while the \textit{Policy Agent} receives this report alongside the specific security policies. This separation prevents a single hijacked agent from both fabricating context and authorizing a bypass.

\textbf{Tool-Use Scoping}: Unlike general-purpose autonomous agents, the sentinel does not possess open-ended tool-use privileges. The LLM agents operate within a "read-only" reasoning sandbox; they can only generate a structured \texttt{EnforcementAction} (DENY, PERMIT, or ESCALATE). The actual "writing" to the security infrastructure (e.g., blocking an IP via Wazuh) is performed by a deterministic, non-LLM \textit{Enforcement Controller}. This architectural decision ensures that even a prompt-injected LLM cannot "command" the firewall to perform arbitrary actions beyond the predefined set of safe enforcement states.

\textbf{Least-Privilege Reasoning}: The sentinel adheres to least-privilege principles by restricting the LLM's influence to the "semantic resolution" of existing policy conflicts. The agentic layer cannot create new policies or modify the Layer 0 blocklist. Furthermore, the threshold-based decision logic ($\tau = 0.75$) serves as a "probabilistic circuit breaker"---any reasoning that cannot meet high semantic certainty defaults to a DENY state, effectively containing the potential impact of LLM hallucinations.

\subsection{Governance and Systemic Risk Management}

Delegating runtime authorization to probabilistic LLM reasoning introduces systemic risks that must be managed through clear governance and fallback strategies.

\textbf{Availability and Fallback}: To mitigate "outage-induced false denies" caused by API latency or service unavailability, the sentinel implements a \textit{Dual-Mode Fallback}. If the LLM agents fail to respond within a 150ms timeout, the system defaults to Layer 0 (Deterministic) enforcement. In this state, "unambiguous" requests are still handled, while "semantically complex" requests are diverted to an \textbf{Escalation Queue} (fail-secure) for human review or cached-policy enforcement. This ensures that system availability is not coupled to cloud API reliability.

\textbf{Integrity and Governance}: To address integrity risks such as prompt injection or jailbreaking, the sentinel employs \textit{Semantic Guardrails} and mandatory \textit{Audit Trails}. Every agent reasoning step is logged as a "Policy Explanation" in the SIEM, allowing SOC operators to detect and revert hallucinated permits. Furthermore, our use of a multi-agent "consensus" model (Layer 3) acts as an internal governance layer, where the Auditor Agent must verify that the Policy Agent's decision strictly aligns with the provided policy context, neutralizing single-point-of-failure injection attacks.

\textbf{Privacy and Data Sovereignty}: Sending sensitive IoT metadata (e.g., user IDs, geolocation) to third-party APIs incurs a "privacy tax." While our current evaluation uses cloud-based Groq inference, our architectural roadmap emphasizes \textbf{Local Differential Privacy (LDP)} and on-premise offloading (Section~\ref{sec:future_work}). By identifying and redacting Personally Identifiable Information (PII) at Layer 0 before it reaches the semantic layer, the sentinel minimizes the data exposure surface without sacrificing reasoning quality.

\section{Limitations and Future Work}

\subsection{Real Device Deployment Considerations}

\subsubsection{Current Evaluation Scope}

Our evaluation uses \textbf{simulated Wazuh alerts} generated from synthetic test scenarios. While the decision pipeline and enforcement integration are production-ready, alerts represent hypothetical IoT access attempts rather than live device traffic. This controlled approach enabled comprehensive adversarial testing (103 scenarios across 7 attack types) and fair baseline comparison, but limits claims about field deployment performance.

\subsubsection{Deployment Feasibility}

\textbf{Wazuh Agent Requirements}: The Wazuh agent (ossec-agent) has minimal resource requirements compatible with many IoT devices:
\begin{itemize}
    \item \textbf{Memory}: 8-32 MB RAM (varies by configuration)
    \item \textbf{CPU}: ARM or x86 architecture
    \item \textbf{Storage}: $\sim$10 MB disk space
    \item \textbf{Network}: Intermittent connectivity sufficient (agents buffer logs locally)
\end{itemize}

\textbf{Supported Platforms}: Wazuh agents run on Linux (including Raspberry Pi, BeagleBone), Windows IoT, and several embedded systems. High-end IoT devices (smart cameras, industrial sensors, edge gateways) can feasibly host agents. Ultra-constrained devices (Arduino, ESP8266) would require gateway proxy deployment.

\subsubsection{Enforcement Integration}

The system integrates with Wazuh Active Response API for distributed IP blocking. Testing was conducted in a \textit{development environment} with Docker containers simulating IoT agents. Production deployment requires:
\begin{itemize}
    \item Network firewall configuration for enforcement targets
    \item Agent authentication with Manager (SSL certificates)
    \item Testing fail-safe behavior under network partition
\end{itemize}

\textbf{Gateway Deployment Option}: For constrained devices, a \textit{reverse proxy gateway} running Wazuh agents can monitor traffic for multiple backend devices, reducing per-device overhead while maintaining centralized access control.

\subsection{Dataset Realism and Generalization}

\subsubsection{Synthetic Dataset Justification}
The primary limitation of our current evaluation is the reliance on a synthetic dataset (103 scenarios) derived from policy author assumptions. This choice was a deliberate design decision to maximize \textbf{scientific control} over the evaluation of the semantic reasoning layer. Public datasets like UNSW-NB15 or IoT-Dev-2024, while ecologically valid for network patterns, lack the fine-grained semantic metadata and "policy-ground truth" labels (e.g., M0801-specific authorization conflicts) required to benchmark LLM reasoning depth. By using author-defined labels, we isolate the sentinel's ability to align complex natural language intent with defined security policies—a prerequisite for assessing generalizability before field deployment.

\subsubsection{Generalization and Distribution Shift}
A significant open question is how the system generalizes to cross-site environments or shifts in device behavior distributions. Our current evaluation assumes a static relationship between user roles and device metadata. In real-world operator workflows, these relationships are dynamic. We acknowledge that the "semantic reasoning" of the LLM may exhibit distribution shift when encountering novel device types not present in our categorical definitions.

\subsubsection{Roadmap for Real-World Validation}
To address the lack of ecological validity in this pilot study, future work will focus on:
\begin{enumerate}
    \item \textbf{Cross-Dataset Validation}: Evaluating the pipeline against real-world traces to assess robustness against noise and distribution shifts in network behavior.
    \item \textbf{Human-in-the-Loop (HITL) Study}: We plan to conduct a validation study where professional SOC analysts are presented with LLM-generated reasoning explanations and asked to verify their alignment with actual operational policies. This will confirm the real-world utility of the system's "auditable reasoning" beyond author-defined ground truth.
    \item \textbf{High-Fidelity Testbed Integration}: Deploying the sentinel in a live IoT testbed simulating standard office and industrial environments to capture operational logs and evaluate steady-state performance.
\end{enumerate}

\subsection{Additional Limitations}

\begin{itemize}
    \item \textbf{Single LLM Model}: Evaluated only Llama 3.3 70B (Groq). Performance may vary with other models.
    \item \textbf{API Dependency}: 34 test failures due to rate limiting demonstrate reliance on external LLM API. Mitigation: local model deployment or caching layer.
    \item \textbf{Policy Scope}: Evaluated on access control policies only. Other IoT security aspects (firmware updates, data encryption) not addressed.
\end{itemize}

\textbf{Code Availability}: Complete source code, test scenarios (103 JSON files across 7 categories), system prompts, and baseline implementations are publicly available at \texttt{https://github.com/ahmed-fouad-lagha/IoT-Access-Sentinel} to facilitate reproduction and extension of this work.
\subsection{Future Research Directions}

While our hybrid architecture demonstrates the effectiveness of zero-shot general-purpose LLMs for IoT access control, several promising avenues warrant further investigation.

\subsubsection{Domain-Specific LLM Fine-Tuning}
The current system leverages pre-trained general-purpose models (Llama 3.3 70B), which demonstrates broad generalizability but incurs API costs and latency. Fine-tuning smaller domain-specific models (e.g., Llama 3 8B) on IoT-specific threat patterns could achieve sub-50ms inference times compared to the current 150ms cloud API calls, enabling real-time edge deployment while eliminating external dependencies.

The current system leverages pre-trained general-purpose models (Llama 3.3 70B), which demonstrates broad generalizability but incurs API costs and latency. Fine-tuning smaller domain-specific models (e.g., Llama 3 8B) on IoT-specific threat patterns could yield several benefits:

\textbf{Latency Reduction}: Smaller fine-tuned models deployed on-premise could achieve sub-50ms inference times compared to the current 150ms cloud API calls, enabling real-time edge deployment scenarios.

\textbf{Cost Elimination}: Local inference eliminates per-request API costs (\textasciitilde\$0.01/request), making the solution economically viable for large-scale IoT deployments with millions of daily access decisions.

\textbf{Enhanced Privacy}: On-premise models eliminate external API dependencies, addressing privacy concerns in sensitive environments such as healthcare IoT or critical infrastructure.

\textbf{Alternative Baseline Benchmarking}: While we used a production-representative RBAC baseline, a primary avenue for future work is a quantitative benchmark against a \textbf{semantic rule-engine} (e.g., OPA/Rego enhanced with graph-based context retrieval). This would allow for a direct comparison between "shallow" rule-based reasoning and the "deep" semantic reasoning provided by LLMs.

\textbf{Specialized Accuracy}: Training on curated datasets of IoT-specific attacks (device impersonation, semantic policy evasion, time-based bypasses) could improve detection rates beyond the current 94.2\% accuracy.

\subsubsection{Feasibility Analysis: Edge Offloading and Model Compression}

To address the latency and cost overhead of cloud-based APIs, we evaluate the feasibility of localizing the sentinel's semantic layer via on-device LLM offloading and model compression. 

\textbf{Model Compression}: Current benchmarks for Llama-3-8B~\cite{llama3} quantized to 4-bit integer (INT4) using llama.cpp demonstrate a reduction in memory footprint from 32~GB (FP32) to approximately 5.5~GB. This compression enables the sentinel to run on commodity edge hardware such as the Raspberry Pi 5 (8~GB RAM) or NVIDIA Jetson Orin Nano. While quantization can incur a minor accuracy penalty (typically $<$1–2\% in MMLU tasks), the gain in data sovereignty and cloud-independence is critical for IoT security.

\textbf{Latency and Throughput}: On-device inference for short security alerts (averaging 50--100 tokens) achieves 3--7 tokens per second on an RPi~5. This translates to an end-to-end enforcement latency of 2--4~seconds. While significantly slower than our current Groq-based LPU implementation (97~ms), this overhead is acceptable for reactive security blocking in most IoT contexts where "fail-secure" policies (deterministic Layer 0) provide immediate protection while the LLM conducts deep semantic forensic analysis.

\textbf{Cost and Sustainability}: Transitioning to localized 4-bit models eliminates the Groq API cost (\textasciitilde\$0.01 per request), making the system economically viable for large-scale enterprise deployments managing thousands of IoT gateways.

\subsubsection{Architectural Hybridization: Semantic Leases}

A promising future direction is the hybridization of our runtime reasoning with CollabIoT-style formal token models. We propose the concept of \textbf{Semantic Leases}—where the agentic sentinel generates short-lived, machine-enforceable access tokens (e.g., Macaroons or JWTs) that encode semantic predicates rather than just rigid identities. In this model, the LLM provides the "intent-aware" validation at the start of a session or when context shifts, while a lightweight edge controller performs sub-millisecond enforcement of the lease. This would combine the sentinel's "deep" reasoning with the extreme performance of hardware-accelerated token validation, effectively removing the LLM from the high-frequency packet enforcement hot-path while retaining its semantic oversight.

Key research questions include: (1) Can a 7B parameter fine-tuned model match GPT-4-class accuracy while reducing inference time by 3×? (2) What is the optimal training data composition (legitimate vs. attack scenarios) for IoT threat detection? (3) How does model size affect the accuracy-latency tradeoff in production access control systems?

Dataset requirements would include 10,000+ labeled IoT access scenarios spanning diverse device types, policy violations, and representative attack vectors, requiring collaboration with industry partners managing large-scale IoT deployments.

\subsubsection{Reproducibility and Open-Source Artifacts}

To ensure scientific reproducibility and facilitate community adoption, we release the complete artifact suite for IoT-Access-Sentinel. The repository is structured as a "Reproducibility Lab," containing:

\begin{itemize}
    \item \textbf{Exact Prompt Templates}: All LLM instructions used in our multi-agent chain are externalized in \texttt{decision\_engine/prompts/}, including the system messages and context-extraction templates.
    \item \textbf{Standardized Scenario Suite}: The 103 test scenarios (Section~\ref{sec:evaluation}) and 105 red-team adversarial cases (Table IV) are provided in serialized JSON format in \texttt{tests/synthetic\_v2/} and \texttt{tests/red\_team/}.
    \item \textbf{Benchmarking Infrastructure}: A "one-click" reproduction script (\texttt{tools/run\_baseline\_comparison.py}) is provided to regenerate all tables and statistical findings reported in this paper.
\end{itemize}

This level of transparency addresses the systemic "black-box" issue in LLM-based security research, providing a verifiable benchmark for future hybrid access control systems.

\section{Conclusion}

We presented IoT-Access-Sentinel, a hybrid multi-agent framework that bridges the "semantic gap" in IoT security by combining deterministic authorization rigors with LLM-based contextual reasoning. Our evaluation on 103 test scenarios demonstrates a statistically significant 16.5 percentage point accuracy improvement over a production-representative RBAC baseline (94.2\% vs 77.7\%, $p < 0.01$). Critically, the system successfully neutralized all \textbf{105 red-team adversarial attempts} across 10 distinct attack categories, validating its robustness against sophisticated evasion. By integrating with the Wazuh SIEM ecosystem, the sentinel provides a production-ready pathway for operations teams to automate semantically complex policies that escape static rules. This work not only achieves high-integrity decisions but also demonstrates operational resilience through its fail-secure architecture, providing a robust and reproducible foundation for the future of agentic IoT security.
